# NetworkSec backend optimization audit

**Audit date** 2026-11-24 · **Branch** `grafana-only` · **HEAD and comparison base** `5527465` plus the existing uncommitted Grafana-only changes.

Keep the API, processor, and optional bot in their current separate processes. Keep PostgreSQL as the authority for incident state and Loki as the searchable telemetry store. The first optimization to measure is connection reuse. Repeated topology work, unused alert-list projections, and processor and bot I/O are stronger candidates than removing routes or merging services. Before widening access, separate PostgreSQL database ownership from runtime credentials and verify who can query Grafana’s Loki datasource.

## Scope and verification

- Matched the in-memory runtime OpenAPI routes, the generated spec, and the checked-in spec. They contain **41 operations on 34 paths** across 27 GET, 8 POST, 4 PATCH, and 2 DELETE operations. `/health` is the unversioned process probe. Development also exposes JSON at `/openapi.json`. [App assembly](../app/main.py#L96) · [OpenAPI](openapi.json).
- Passed **44 targeted tests** using in-process clients and fakes, with pytest’s repository cache disabled, and validated the Compose model across all profiles using `.env.example`. The test run emitted the existing Starlette TestClient `httpx` deprecation warning. The previous refactor recorded 321 passes with disposable PostgreSQL and Loki. The current audit used source, installed dependency metadata, and tests without exercising a live PostgreSQL, Loki, Telegram, Docker stack, or GNS3 lab. [Previous functional verification](grafana-only-refactor.md#verification).
- **Verified** means observed in this tree, the in-memory contract, or the checks above. **Inference** means a likely consequence of the implementation or a conditional deployment risk. **Estimate** means a capacity-planning assumption or acceptance target. Live query plans, traffic, dataset size, engine versions, actual VM/container resource use, and external API consumers remain unverified. The published [performance preflight](performance.md) describes earlier local batches. It supplies historical context for test design.

**Proposed architecture**

```text
Lab devices -> rsyslog -> raw evidence and processor JSONL
                              |
                    single processor + SQLite checkpoints/journal
                       |                         |
                  Loki logs              PostgreSQL catalog, incidents,
                       |                 history, registry, rules and outbox
                       |                   |           |              |
                       +----> Grafana <----+      FastAPI JSON    optional bot
                                  (view-only SQL)                 -> Telegram
```

Keep synchronous SQL off the bot event loop and use bounded HTTP and database connections in their owning processes. Give migration execution a distinct deployment identity, with readiness after successful schema verification. Provision a Grafana SQL reader independently. Retain single-node Loki and the current checkpoint and outbox approach on the VM. A future process split beyond today’s boundaries needs measured CPU, failure-isolation, or availability evidence. Co-locating API and processor would couple request latency, deployment restarts, ingestion backlog, and spool access. Small pools can increase idle backend memory and can create queueing, so capture both request tails and resident use before adopting them.
